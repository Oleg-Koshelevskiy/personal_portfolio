# 0001. Rationale: оновлення стеку

_Історія рішення для [index.md](./index.md). Для збірки не потрібна._

## Context

Сайт зараз на Next.js 13.5.5, React 18, Tailwind 3, `framer-motion` 10, `resend` 1, ESLint 8 з `next lint`. Розгорнутий на Vercel. Код невеликий: близько 20 файлів, одна сторінка, один маршрут API (`app/api/send/route.ts`). Тестів немає.

Що тисне:
- **Безпека і підтримка.** Гілка 13.x не отримує виправлень. Для фреймворку, що обробляє запити на сервері, це реальний ризик.
- **Порядок робіт.** У scope далі йдуть сторінки кейсів, SEO, дві мови і блог. Якщо писати їх на 13.5, потім доведеться переписувати під нові API (асинхронні `params`, новий лінт, Tailwind 4).
- **Ламкі місця в коді**, які зачепить оновлення: `next lint` прибрано в новому Next; `resend` новіших версій повертає `{ data, error }` замість винятку (exception); Tailwind 4 прибрав `bg-opacity-*` і `placeholder-[…]` та змінив шкалу `rounded`; `EmailSection` імпортує SVG за абсолютним шляхом `/public/...`, який з Turbopack (новий збирач Next) може не спрацювати; `tailwind.config.ts` перевизначає всю палітру через `theme.colors`.
- **Немає тестів**, тож «виглядає як раніше» перевіряється лише очима, за знімками до і після.

> ⚠️ Premise note: перехід на React 19 сам несе ризик. Наприкінці 2025 року в React Server Components знайшли критичні вразливості, виправлені лише в нових patch версіях. Тож «оновити до 19» означає «оновити до останньої виправленої версії 19.x», а не до будь якої 19. Це закриває AC-8 (аудит без high і critical).

## Options considered

### Option 1: Консервативно, до Next 14 або 15
Мінімальний крок до версії з меншими змінами. **Pros**: менше правок, React 18 лишається (для 14). **Cons**: 14 уже без підтримки, 15 скоро втратить її; оновлення доведеться повторювати якраз під час роботи над новими фічами.

### Option 2: Остання стабільна одним кроком через codemod, Tailwind 4 окремим кроком (обрано)
`@next/codemod upgrade` відразу до цільової версії, далі окремими зрізами лінт, `motion`, Tailwind 4. **Pros**: найдовша підтримка; на такому малому коді codemod робить майже все; Tailwind окремо, тож поломку вигляду легко локалізувати. **Cons**: найбільший стрибок поведінки за раз (кеш, Turbopack за замовчуванням); якщо збірка зламається на першому кроці, причин може бути кілька одночасно.

### Option 3: Поетапно 14, 15, 16
Кожна мажорна версія окремо, зі збіркою і перевіркою. **Pros**: кожна поломка прив'язана до однієї версії. **Cons**: три цикли замість одного для 20 файлів, без вигоди: тут немає `middleware`, асинхронних `params` чи складного кешування, які зазвичай ламаються між версіями.

### Option 4: Новий проєкт через `create-next-app` і перенос компонентів
**Pros**: чистий шаблон конфігів. **Cons**: губиться історія файлів, легко загубити дрібниці (`cv.pdf`, іконки, метадані); для такого коду це переписування без потреби.

## Rationale

Код малий і простий: немає `middleware`, динамічних маршрутів чи кешування даних, тобто саме тих місць, що ламаються між мажорними версіями Next. Тому поетапний перехід (Option 3) коштує втричі більше і майже нічого не дає, а консервативна версія (Option 1) лише відкладає ту саму роботу на момент, коли нових фіч уже буде більше. Tailwind винесено окремим зрізом, бо це єдина частина, що реально змінює вигляд, а без тестів поломку вигляду треба мати змогу прив'язати до одного кроку.

Форму контакту свідомо не виправляємо (статуси, перевірка полів, лог даних відвідувача): це зміна поведінки, вона належить фічі 8, і змішувати її з оновленням означало б ускладнити перевірку «працює як раніше».
